# 6. できること・できないこと

## 判断原則

カスタム推奨事項で判定できるのは、割り当て範囲の最新 `RawEntityMetadata` 行から KQL で証明できることです。必要な資産行または API フィールドがなければ、KQL を複雑にしても証拠は増えません。

## できること

| 能力 | 条件 | 製品内の参考ユースケース |
|---|---|---|
| 単一フィールドの判定 | 対象設定が `Record` にある | KMS キーの削除待ち |
| ネスト値・配列の判定 | API 構造が `Record` にある | ルートテーブルの過剰な VPC Peering |
| 現在値に含まれる日時との比較 | 日時が `Record` にある | 停止から30日超の EC2 |
| 複数資産型の関連付け | 両方の型が割り当て範囲にある | CloudTrail と Trail Status |
| 任意の関連レコードの判定 | 親資産と関連レコードに共通キーがある | EBS Snapshot と CreateVolumePermission |
| 関連資産の不在判定 | 判定結果を付ける親資産がある | VPC に Active Flow Log がない |
| 健全・不健全集合の統合 | 最終的に各資産行を返せる | 未使用セキュリティグループ |
| ポリシー文書の内容判定 | ポリシー JSON が `Record` に収集される | ECR、S3、IAM ポリシー |

## できないこと

| 要件 | 制約 | 代替策 |
|---|---|---|
| AWS/GCP を1推奨事項で評価 | 複数環境は非対応 | 環境ごとに推奨事項を作る |
| 構成変更履歴や任意 Timespan の分析 | 最新レコードが評価対象 | CloudTrail、Cloud Audit Logs、SIEM を使う |
| `Record` にない設定の判定 | APIレスポンス以上の情報はない | 別 API の収集、組み込み推奨事項を使う |
| ライブ疎通や攻撃シミュレーション | 構成メタデータ評価である | 専用スキャナー、接続テストを使う |
| データ内容や保存オブジェクトの検査 | データプレーン内容は含まれない | DSPM、DLP、クラウドネイティブ検査を使う |
| 起点資産も存在しない状態の架空行出力 | `HealthStatus` を付ける行がない | アカウント等の親資産を起点にできるか確認する |
| 割り当て範囲外の完全な横断評価 | 評価は割り当て資産に対して実行 | 割り当て設計を見直す |
| 自動修復 | KQL は読み取り専用 | Workflow Automation 等を別途構成する |

## 追加例から確認できた設計上の制限

- 同じ `Identifiers.Type` でも `Record` の形が一様とは限らず、型名だけでは対象行を特定できません。
- `join`、`leftouter`、`leftanti`、`in` は割り当て範囲内の行だけを使用します。関連レコードが未収集または範囲外なら、存在しないものとして誤判定する可能性があります。
- 資産名だけの相関は、複数アカウント・リージョンで衝突する可能性があります。必要に応じて `Identifiers.AmazonAccountId` と `AdditionalData.Region` を含む複合キーが必要です。
- ポリシー JSON を解析できても、評価対象は収集された文書に限られます。ポリシーの実効権限、SCP、Permission Boundary、リソースポリシー等を自動的に総合評価するものではありません。
- 製品内参考KQLはすべてが HELP の登録契約を満たす完成形ではありません。省略された `iff` と必須7列は登録時に補います。

したがって、追加された例によって履歴、複数環境、未収集情報、データプレーン、自動修復に関する制限が解除されるわけではありません。

## IAM ユーザー・グループとロールの判定

AWS IAM では、IAM ユーザーまたはIAMグループへロールを直接「割り当てる」構造ではありません。ユーザーがロールを引き受けるには、通常、次の両側を満たす必要があります。

1. ユーザーへ直接、または所属グループのポリシー経由で、対象ロールに対する `sts:AssumeRole` が許可されている。
2. 対象ロールの信頼ポリシーが、そのユーザー、ロール、アカウント等のPrincipalを信頼している。

IAMグループは認証主体ではないため、ロール信頼ポリシーの `Principal` にはできません。「グループにロールが割り当てられているか」は、「グループポリシーが、そのメンバーに対象ロールの `sts:AssumeRole` を許可しているか」と読み替えます。

| 判定したいこと | カスタム推奨事項での可否 | 必要なレコード |
|---|---|---|
| ユーザーに管理ポリシー／インラインポリシーが関連付く | 条件付きで可能 | ユーザーとポリシーの関連レコード |
| グループにポリシーが関連付く | 条件付きで可能 | グループとポリシーの関連レコード |
| ユーザーが対象グループに所属する | 条件付きで可能 | ユーザー・グループのメンバーシップレコード |
| ポリシー文書が対象ロールへの `sts:AssumeRole` をAllowする | 条件付きで可能 | 関連ポリシー、既定バージョン、ポリシー文書 |
| ロール信頼ポリシーが対象Principalを許可する | 条件付きで可能 | ロールと信頼ポリシー文書 |
| ユーザーが実際にロールを引き受けられる | 原則として構成レコードだけでは断定不可 | 上記に加え、明示的Deny、SCP、Permission Boundary、条件、セッションポリシー、リクエストコンテキスト等 |

製品内参考KQLには `iam.policyuser`、`iam.policygroup`、`iam.policyrole`、`iam.policyversion` があるため、収集済みのポリシー関連付けと文書を結合する構成検査は可能です。ただし、ユーザー・グループのメンバーシップやロール信頼ポリシーに必要な型・フィールドが実環境の Categories と `Record` に存在するかは別途確認が必要です。存在しなければ、カスタム推奨事項だけでは完全な判定を作れません。

完全な実効権限の確認には、AWS IAM Access Analyzer、IAM Policy Simulator、CloudTrail の `AssumeRole` イベントなどを併用します。

## 要件判定フロー

1. 対象は AWS または GCP のどちらか1環境か。
2. 健全性を付ける対象資産の `RawEntityMetadata` 行があるか。
3. 必要な設定値が `Record` にあるか。
4. 関連資産が必要なら同じ割り当て範囲で取得できるか。
5. 関連キーはアカウント・リージョンを含めて一意か。
6. 同じ型に必要な `Record` 形状の行が存在するか。
7. 最新状態の判定で要件を満たせるか。
8. null、API既定値、未収集を区別できるか。

1つでも満たせない場合は、カスタム推奨事項だけでの実装を止め、代替データソースを設計します。
