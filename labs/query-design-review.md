# 設計レビュー演習: できること・できないこと

## 目標

要件を KQL に書き始める前に、`RawEntityMetadata` だけで実現可能かを判定し、適切な製品内参考ユースケースを選びます。

## 課題1: 実現可否を分類する

次の要件を「可能」「条件付きで可能」「不可」に分類し、必要な `Identifiers.Type` と `Record` フィールド、または代替策を記入します。

| 要件 | 分類 | 根拠・必要な証拠 |
|---|---|---|
| KMS キーが削除待ちか確認する |  |  |
| VPC に Active Flow Log がないことを確認する |  |  |
| 過去90日のセキュリティグループ変更回数を数える |  |  |
| AWS と GCP の公開 VM を1つの推奨事項で評価する |  |  |
| CloudTrail の CloudWatch Logs 配信が直近1日以内か確認する |  |  |
| S3 オブジェクト内に個人情報があるか検査する |  |  |

## 課題2: 製品内パターンを選ぶ

各要件に最も近いパターンを選びます。

- 単一資産の `iff`
- `mv-expand` による配列評価
- `join` による関連資産評価
- `leftouter` による任意の関連資産評価
- `leftanti` による関連資産不在の評価
- `union` による健全・不健全集合の統合
- `in` / `!in` による補助集合との照合
- `parse_json` によるポリシー文書の解析
- `Record` 内日時と `ago()` の比較

## 課題3: 出力契約をレビューする

製品内 AWS 参考 KQL から1例を選び、次を確認します。

1. `Environment` と `Identifiers.Type` が指定されている。
2. 対象資産すべてに `HEALTHY` または `UNHEALTHY` が付く。
3. 最終結果に必須7列がある。ない場合は `project` を追加する。
4. Timespan や不要な ARN 固定フィルターがない。
5. 欠損フィールドを設定不良と誤認していない。
6. 同じ型の `Record` 形状と実行時型を確認している。
7. 関連付けに使うキーがアカウント・リージョンを跨いでも一意である。
8. `iff` と必須7列が省略された製品例は、HELP の契約に合わせて補完している。

## 課題4: 複数スコープでの相関をレビューする

ECR、S3、CloudTrail のいずれかの参考例を選び、同じ資産名が2つのAWSアカウントまたはリージョンに存在する場合を想定します。

1. 現在の相関キーだけで誤結合しないか確認する。
2. `Identifiers.AmazonAccountId` と `AdditionalData.Region` のうち必要なスコープを特定する。
3. 補助クエリと親資産クエリの両方に同じ複合キーを追加する。
4. 関連レコード未収集時に `HEALTHY` または `UNHEALTHY` と断定してよいか説明する。

## 模範分類

| 要件 | 分類 | 理由 |
|---|---|---|
| KMS 削除待ち | 可能 | `kms.key` の現在の `Record.KeyState.Value` を判定 |
| VPC Flow Log 不在 | 条件付きで可能 | VPCを親行にして Active Flow Log と `leftanti` できる場合 |
| 過去90日の変更回数 | 不可 | 最新構成であり変更履歴ではない |
| AWS/GCP の同時評価 | 不可 | 1推奨事項で複数環境は非対応 |
| Trail の直近配信 | 条件付きで可能 | `cloudtrail.trailstatus` と日時が収集される場合 |
| S3 内の個人情報 | 不可 | オブジェクト内容は構成メタデータではない |

## 完了条件

- 製品内資料の該当箇所を根拠として説明できる
- 実現できない要件に代替データソースを提示できる
- 実現可能な要件では、対象型、証拠フィールド、KQLパターン、出力契約を定義できる
- 複数アカウント・リージョンで安全な相関キーを定義できる
